# 性能基准（StdUnit.Tags.Benchmarks）

> 本目录是**开发期工具**，不进入任何 NuGet 包（Paket 的 `Benchmarks` 组是 `storage: none`，工程 `IsPackable=false`）。
> 它在解决方案内，所以 `dotnet build` 会编译它（防止 API 漂移后悄悄腐烂），但**不**参与 CI 的测试与 AOT 冒烟。

## 这份报告怎么读

- **只用于改动前后对比**：绝对耗时会随机器、runtime、编译选项变化，任何一行都不能当作对外性能承诺。
- 全部为 `-c Release` 构建，开启 `[MemoryDiagnoser]`；`Allocated` 是单次操作的托管分配量。
- 采集环境：

  | 项 | 值 |
  |---|---|
  | 软件版本 | `2.0.0-beta9`（首个对外发布的基线） |
  | 日期 | 2026-11-12 |
  | BenchmarkDotNet | v0.15.8 |
  | .NET SDK | 8.0.129（`net8.0`） |
  | OS | Windows 10 22H2 (10.0.19045) |
  | CPU | Intel Core i7-8700 3.20 GHz，6 物理 / 12 逻辑核 |

## 1. 读遍历（`TagTreeReadBenchmarks`）

一棵 N 个测点的树（均分到 10 个子组），叶子是纯内存假测点、通道是空实现，所以测到的只有读遍历、
访问模式/使能判断与派发，与硬件、网络无关。

| 方法 | 点位 | Mean | Allocated |
|---|---|---|---|
| `NoOp`（基线） | — | 0.24 ns | 0 B |
| `ReadAsync` | 1 000 | 8.80 µs | **0 B** |
| `ReadAsync` | 10 000 | 92.22 µs | **0 B** |

`NoOp`（直接返回 `Task.CompletedTask`，0 B）用来证明 `Allocated` 列不是基准装置自身的开销。

**结论**：读遍历每点约 **8.8–9.2 ns**，线性；**整轮零分配**。1 万点位的读约 0.092 ms。
写遍历见 §2。

### 1.1 读遍历的成本拆解（`TraversalBreakdownBenchmarks`，10 000 个扁平叶子）

| 逐层加回成本 | 总计 | 每点 |
|---|---|---|
| 纯数组遍历 | 4.91 µs | 0.49 ns |
| + 访问模式解析（`SearchAccessMode`，**未走缓存**） | 62.26 µs | 6.23 ns |
| + 派发 + 完成检查 | 19.62 µs | 1.96 ns |
| + 策略判断（R1W/WO）与派发 | 74.46 µs | 7.45 ns |
| 实际遍历（`TagUnion.ReadAsync`，含访问模式缓存命中） | **78.50 µs** | **7.85 ns** |
| `IsDirty`（经 `TagUnion` 分发） | 50.85 µs | 5.09 ns |
| `IsDirty`（扁平数组 + 直接读 `ITag.IsDirty`） | **23.95 µs** | **2.39 ns** |

**结论**：逐级冒泡解析访问模式本身要 6.2 ns/点，但它是**配置期属性**，解析结果缓存在
`TagUnion.CachedAccessMode` 上，热路径只做一次空值检查——所以实际遍历低于"裸解析"。
剩下的就是每个节点必须做的记账（一次派发 + 策略判断 + 状态回写），已经接近下限。

## 2. 写遍历：干净 vs 少量脏 vs 全脏（`TagTreeDirtyWriteBenchmarks`）

叶子是纯内存假测点（写方法不做设备 IO），因此量的是**框架的派发开销**；"脏"叶子用永不自动清脏的假测点表示，
所以不需要在迭代间重置状态。「0% 脏」那一列就是运行器在"无脏数据"时**跳过**的动作（见第 9 节）。

| 点位 | 0% 脏 | 1% 脏 | 100% 脏 |
|---|---|---|---|
| 1 000 | 8.02 µs | 7.93 µs | 8.13 µs |
| 10 000 | 83.80 µs | 81.10 µs | 86.87 µs |

**结论**：写遍历的成本几乎全部来自**遍历本身**（每节点约 8 ns），"有多少节点真的被写"只带来个位数百分比的差异。
所以"干净时跳过写遍历"（第 9 节）比"让写更便宜"更有价值。真实设备的写入耗时不在本表内。

## 3. `CbntFanOutBenchmarks` — “数千点位”的现实形态

一次硬件读之后，把值分发给 N 个子测点（组合式测点）。这是 5 000 点位项目的真实形状；
“N 个独立测点各读一次”是 N 次设备往返，现实中不存在，因此不作为基准。

| 子测点数 | Mean | Allocated |
|---|---|---|
| 1 000 | 2.12 µs | 72 B |
| 5 000 | 15.60 µs | 72 B |

**结论**：每点 **2.1–3.1 ns**，逐点零分配（那 72 B 是基准桩里 `Task.FromResult` 的固定开销，不是框架的）。

## 4. `S7ChannelReadBenchmarks` — 读一块 DB

用桩 `S7Client`（只占位、立即返回 0），测的是**我们这层**：地址解析、互斥体、`Span` 传递、错误码检查。

| 字节数 | Mean | Allocated |
|---|---|---|
| 1 000 | 606.3 ns | 832 B |
| 20 000 | 601.9 ns | 832 B |

**结论**：单次读 < 1 µs，分配与字节数无关（零拷贝，缓冲区由调用方提供）。
**真实耗时里 PLC 响应占绝对多数**，这组数字的用途是确认“我们不是瓶颈”。
那 832 B 只发生在**直读点位**（`DirectTag`，兜底用法）——地址在每轮解析；组合式测点的地址只在加载期解析一次。

## 5. `ModbusCbntReadBenchmarks` — 通道数组的分配

组合式测点每轮读；用桩通道对比“每轮返回新数组”（NModbus 的形状）与“写入调用方预分配数组”。

| 寄存器数 | 通道返回新数组 | 复用缓冲区 | 耗时 |
|---|---|---|---|
| 32 | 160 B | 72 B | 30–35 ns |
| 125 | 352 B | 72 B | 30–40 ns |

**结论**：每轮省 88–280 B，耗时无可测差异。按 100 Hz、单入口估算约 9–28 KB/s，
相对一次 Modbus TCP 往返可忽略；而"复用"需要改 `IModbusRegisterChannel` 的公开签名。
**维持现状**（决策记录见 `docs/设计决策与边界/0. 设计决策与边界.md` §五）。

## 6. `MetricRecordingBenchmarks` — 打点开销

| 场景 | Mean | Allocated |
|---|---|---|
| 无监听者（默认部署） | 3.77 ns | 0 B |
| 有 `MeterListener` | 5.68 ns | 0 B |

**结论**：没人订阅时零分配、纳秒级，所以指标常开没有代价；订阅后每轮多 ~2 ns。

## 7. 内存：1000 个点和 10000 个点，有影响吗？

要分两种"内存"看：

| | 是什么 | 与点位数的关系 |
|---|---|---|
| **每轮分配** | 每轮采集新产生的垃圾（`[MemoryDiagnoser]` 的 `Allocated`） | **无关**：都是 0 B |
| **常驻内存** | 加载后一直活着的对象图（测点、组合子、描述符） | **线性**：点位数 × 每点约 350–400 B |

### 7.1 每轮分配：0 B，与点位数无关

遍历、组合分发、指标记录的 `Allocated` 都是 0（组合分发表里的 72 B 来自基准桩）。
10 Hz × 10k 点位也不会产生可观测的 GC 压力。

### 7.2 常驻内存：严格线性

用 `--footprint` 测量（构建对象图前后各一次 full GC，取 `GC.GetTotalMemory(true)` 差值）：

| 形态 | 1 000 点 | 10 000 点 | 50 000 点 | 每点 |
|---|---|---|---|---|
| 树形（10 个子组） | 0.42 MB | 3.80 MB | 18.66 MB | ~391–440 B |
| 组合式（1 Cbnt + N 子测点） | 0.34 MB | 3.31 MB | 16.53 MB | ~347 B |

- 常驻内存是**一次性、线性**的：1 万点位约 **3.3–3.8 MB**，5 万点位约 **16.5–18.7 MB**（托管对象图，不含 XML 源文本与业务数据），不构成部署障碍。
- 组合式比树形略省（少一层测点对象与 `TagUnion` 包装），密集点位优先用组合式。
- 这是**下限**：真实项目还会持有 XML、字符串与业务侧对象。

> 判断口径：**看"每轮分配"决定要不要优化**（影响 GC 频率），**看"常驻内存"决定能装多少点**（一次性的堆占用）。

## 8. `EnsureConnectedBenchmarks` — 每轮“我还活着吗”的成本

`TagGrpRunner` 每轮、每个通道都会 `EnsureConnectedAsync(force:false)`。Modbus 的存活探测用
`Socket.Poll(SelectRead)` + `Available == 0` 判定，当前实现用 **0 超时**（非阻塞）；
下表同时给出带超时的版本作对照——`Poll(1000)` 在 Windows 上受计时器粒度影响（≈15.6 ms）实际阻塞 **15.8 ms**。

| 方法 | Mean |
|---|---|
| `EnsureConnectedAsync`（已连接，当前实现） | **2.30 µs** |
| 原始 `Socket.Poll(0, SelectRead)` | 1.42 µs |
| 原始 `Socket.Poll(1000, SelectRead)` | 15.82 ms |
| 原始 `Socket.Connected` 标志 | 0.72 ns |

**结论**：每轮每通道的存活探测固定开销约 **2.3 µs**（≈ `Poll(0)` + `Available` 的 ioctl）。
表中 `Poll(1000)` 那一行说明"带超时的探测"在 Windows 上受计时器粒度影响（≈15.6 ms），
因此当前实现采用 0 超时——两者判定逻辑相同，差别只是否等待。

## 9. 运行器判脏索引（`DirtyNodeIndex`）

运行器在每次（重）启动时把入口子树里的 `ITag` / `ITagCbnt` 收进两个扁平数组，判脏变成两次数组扫描；
干净时它还会跳过那趟必然空转的写遍历（§2 的「0% 脏」列，10k ≈ 82 µs）。

| 项目（10 000 节点） | 数值 |
|---|---|
| 判脏：`entry.IsDirty()`（递归 + `TagUnion` 分发） | 50.85 µs（5.09 ns/点） |
| 判脏：扁平索引（直接读 `ITag.IsDirty`） | **23.95 µs（2.39 ns/点）** |
| 干净树上的 `WriteAsync` | 81.36 µs —— **整趟跳过** |

- 索引只收录 `ITag` / `ITagCbnt`，它们正是写单元（`WriteAsync` 只看这两类各自的 `IsDirty`）；
  `ITagCbnt` 可以独立为脏（整块缓存重写），所以必须收录组合本身。
- 正确性依据是 `ITagGrp.IsDirty()` 与 `WriteAsync` 的一致性契约（见接口注释）：
  **返回 false 时写不得有任何动作；只要存在待写节点就必须返回 true**。它**不是**"父脏必有脏子"。
- 等价性由 `DirtyNodeIndexTests` 保证（空树、脏 Tag、脏 Cbnt、嵌套组、混合树反复切换）。

## 结论速览

| 关注点 | 数字 | 含义 |
|---|---|---|
| 框架遍历 | **8.8–9.2 ns/点、每轮 0 B** | 1 万点约 0.092 ms/轮，不产生垃圾 |
| 组合分发 | **2.1–3.1 ns/点、逐点零分配** | 点位多本身不是瓶颈 |
| 判脏 | **2.4 ns/点**（扁平索引） | 10k ≈ 24 µs；干净时还跳过约 82 µs 的空写遍历 |
| 写遍历 | 8 ns/点（10k ≈ 81–87 µs），**与脏比例几乎无关** | 成本在"走一遍"，不在"写多少个" |
| 每轮存活探测（Modbus） | **2.3 µs/通道** | 非阻塞探测（`Poll(0)` + `Available`）的固定成本 |
| S7 通道读 | 0.60 µs/次、832 B | 仅影响DirectTag（非`TagCbnt`的兜底用法），PLC 决定实际耗时 |
| Modbus 通道数组 | 每轮 160–352 B | 不值得改公开接口复用缓冲区 |
| 指标记录 | 3.77 ns / 0 B（订阅后 5.68 ns） | 可常开 |
| 常驻内存 | **~350–400 B/点**；1k≈0.4 MB、10k≈3.5 MB、50k≈17 MB | 一次性、线性，不构成部署障碍 |

## 维护约定

- 新增基准：一个类一个关注点，`[MemoryDiagnoser]` 必开；**必须**能说明“这组数字能/不能得出什么结论”，
  避免把桩实现或回环网络的结果当成端到端性能。
- 基准结果不设门槛（机器差异会让它变成随机红）；它只用来做改动前后对比。
- 改动热路径（遍历、组合通知、驱动读写、判脏）时，请顺手更新本文件的对应表格——**数字过期比没有更糟**。
- 改了点位的对象结构（新增字段/包装层）时，记得重跑 `--footprint`：常驻内存是**每点 ~350 B** 的线性量。
