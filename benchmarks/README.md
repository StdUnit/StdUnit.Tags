# 性能基准（StdUnit.Tags.Benchmarks）

> 本目录是**开发期工具**，不进入任何 NuGet 包（Paket 的 `Benchmarks` 组是 `storage: none`，工程 `IsPackable=false`）。
> 它在解决方案内，所以 `dotnet build` 会编译它（防止 API 漂移后悄悄腐烂），但**不**参与 CI 的测试与 AOT 冒烟。

## 这份报告怎么读

- **只用于改动前后对比**：绝对耗时会随机器、runtime、编译选项变化，任何一行都不能当作对外性能承诺。
- 全部为 `-c Release` 构建，开启 `[MemoryDiagnoser]`；`Allocated` 是单次操作的托管分配量。
- 采集环境：

  | 项 | 值 |
  |---|---|
  | 日期 | 2026-11-11 |
  | BenchmarkDotNet | v0.15.8 |
  | .NET SDK | 8.0.129（`net8.0`） |
  | OS | Windows 10 22H2 (10.0.19045) |
  | CPU | Intel Core i7-8700 3.20 GHz，6 物理 / 12 逻辑核 |

## 1. `TagTreeTraversalBenchmarks` — 框架自身开销

一棵 N 个测点的树（均分到 10 个子组），叶子是纯内存假测点、通道是空实现，所以测到的只有遍历、
使能/脏标记判断与派发，与硬件、网络无关。

| 方法 | 点位 | Mean | Allocated |
|---|---|---|---|
| `NoOp`（基线） | — | 0.24 ns | 0 B |
| `ReadAsync` | 1 000 | 8.45 µs | **0 B** |
| `ReadAsync` | 10 000 | 94.15 µs | **0 B** |

**结论**：每点耗时约 **8.4–9.4 ns**（1k 与 10k 同量级，线性），**整轮零分配**。
1 万点位的框架开销约 0.094 ms，相对一轮真实采集（设备往返 ms 级）可以忽略。

### 1.1 时间花在哪（`TraversalBreakdownBenchmarks`，10 000 个扁平叶子）

| 逐层加回成本 | 每点耗时 | 说明 |
|---|---|---|
| 纯数组遍历 | 0.47 ns | 基线 |
| + 访问模式解析（`SearchAccessMode`，**未走缓存**） | 6.2 ns | 逐级冒泡的裸成本：自身 → 父级 Cbnt → 各级 Grp → 兜底 RW |
| + 派发 + 完成检查 | 1.8 ns | 一次接口调用 + `Task.Status` |
| + 策略判断（R1W/WO）与派发 | 6.6 ns | 上面两项组合（有重叠） |
| `TagUnionExtensions.IsDirty`（每轮另一次全树扫描） | 5.0 ns | 全树干净时走完所有节点 |
| **实际遍历（`TagUnion.ReadAsync`，含缓存命中）** | **8.4–9.4 ns** | 见上表；比"裸解析"低，因为每节点一生只解析一次 |

**瓶颈与结论**：逐级冒泡的**裸解析**是 6.2 ns/点，但**热路径上不会重复付这个钱**——访问模式是配置期属性，
解析结果缓存在 `TagUnion.CachedAccessMode` 上，之后只剩空值检查。所以剩下的就是一次派发 + 策略判断 + 状态回写，
已经接近"每个节点必须做的记账"的下限。要再快就只剩 `IsDirty` 全树扫描改成增量脏标记（语义改动大，暂不做）。

> 历史（2026-11 三轮修复）：
> 1. `1 000 → 72.41 µs / 221.54 KB`、`10 000 → 775.93 µs / 2190.29 KB`：
>    `TagUnionExtensions.ReadAsync/WriteAsync` 通过 `TagUnion.Map` 传三个 `async` 闭包，
>    **每个节点**都要构造闭包 + 委托 + 异步状态机（≈220 B）。改为手动 `switch` 后降到 616 B / 轮。
> 2. `616 B → 0 B`：`TagGrp.Children` / `TagCbnt.Children` 是 `IDictionary`，`foreach` 走接口会**装箱
>    `Dictionary.Enumerator`**（每次遍历一个分配），而它出现在每轮的读、写、判脏与通知路径上。
>    改存具体 `Dictionary`、只让公开属性保持 `IDictionary` 后，分配归零；
>    同一改动把组合分发从 `9.88 µs / 128 B`（1 000 子测点）压到 `2.00 µs / 72 B`。
> 3. `37.47 µs → 12.85 µs`（1 000 点）：`SearchAccessMode` 原来用 `TagContainer.Map` + 两个委托，
>    每点位要查 **两次**（R1W 判定 + `IsWriteOnly`）；改为 `TagContainer.AccessMode` 的 `switch`、
>    只查一次，并给 `ReadAsync` 加了"读同步完成就不进 async 机制"的快路径。
> 4. `12.85 µs → 8.45 µs`（1 000 点）：访问模式改为**逐级冒泡**（修正 `ITag`/`ITagCbnt` 只查一层的旧缺陷），
>    同时按"访问模式是配置期属性"把它缓存在 `TagUnion.CachedAccessMode` 上——每个节点一生只解析一次，
>    之后是空值检查。正确性与速度同时拿到。
> 前两条已写进 `docs/设计决策与边界/0. 设计决策与边界.md` §三：热点路径不要用 `Map` + 闭包，
> 也不要用 `IDictionary` 接口去 `foreach`。

## 2. `CbntFanOutBenchmarks` — “数千点位”的现实形态

真实的场景往往要组合多个测点成为一个`TagCbnt`，从而把N次读写合并成一次`IO`。这个测试正是为这个场景准备的。一次硬件读之后，把值分发给 N 个子测点（组合式测点）。这是 5 000 点位项目的真实形状；而“N 个独立测点各读一次”是 N 次设备往返，现实中不存在，因此不作为基准。

| 子测点数 | Mean | Allocated |
|---|---|---|
| 1 000 | 2.00 µs | 72 B |
| 5 000 | 12.79 µs | 72 B |

**结论**：每点约 **2.6 ns**，逐点零分配（那 72 B 是基准桩里 `Task.FromResult` 的固定开销，不是框架的）。
组合式的分发成本远低于遍历，说明“点位多”本身不是瓶颈。

## 3. `S7ChannelReadBenchmarks` — 读一块 DB

用桩 `S7Client`（只占位、立即返回 0），测的是**我们这层**：地址解析、互斥体、`Span` 传递、错误码检查。

| 字节数 | Mean | Allocated |
|---|---|---|
| 1 000 | 588.9 ns | 832 B |
| 20 000 | 588.0 ns | 832 B |

**结论**：单次读，内存分配与字节数无关（零拷贝，缓冲区是调用方提供的）。
**真实耗时里 PLC 响应占绝对多数**，这组数字的用途是确认“我们不是瓶颈”。

> 历史（2026-11 修复前）：`6.2 µs / 10.49 KB`（两种大小相同）。原因是 `S7AddressParser` 每次 `Parse`
> 都 `new Regex(...)`；提升为 `static readonly` 后降到现在这个水平。剩下的 832 B 来自 `Match`/`S7Address` 的分配，
> 要再压需改成 span 手写解析——目前不值得，已记录为“不做”。

## 4. `ModbusCbntReadBenchmarks` — cache 复用是否值得

组合式测点每轮读；用桩通道对比“每轮返回新数组”（现状）与“写入调用方预分配数组”（需要改公开接口）。

| 寄存器数 | 现状 | 复用 Cache | 耗时 |
|---|---|---|---|
| 32 | 160 B | 72 B | ~32 ns（无可测差异） |
| 125 | 352 B | 72 B | ~31–40 ns（抖动大于差距） |

**结论：不做**。省下 9–28 KB/s（按 100 Hz 单入口估算），代价是 `IModbusRegisterChannel` /
`IModbusBitsChannel` 的公开签名变更（net472 没有默认接口方法兜底）。已记入
`docs/设计决策与边界/0. 设计决策与边界.md` §五“已评估、决定不做”。

## 6. 内存：1000 个点和 10000 个点，有影响吗？

要分两种"内存"看，它们经常被混为一谈：

| | 是什么 | 与点位数的关系 |
|---|---|---|
| **每轮分配** | 每轮采集新产生的垃圾（`[MemoryDiagnoser]` 的 `Allocated`） | **无关**：1k 与 10k 完全相同 |
| **常驻内存** | 加载后一直活着的对象图（测点、组合子、描述符） | **线性**：点位数 × 每点约 350–390 B |

### 6.1 每轮分配：与点位数无关（且已是 0）

| 形态 | 1 000 点 | 10 000 点 |
|---|---|---|
| 遍历 | **0 B / 轮** | **0 B / 轮** |
| 组合式分发 | **0 B / 轮**（基准表里的 72 B 来自桩通道） | 同左 |

也就是说：**高频采集时的 GC 压力与点位数无关，而且框架层当前是零分配**。
2026-11 的两轮修复（`Map`+闭包 → `switch`；`IDictionary` 遍历 → 具体字典）把这件事从
"每节点 220 B"做到了"每轮 0 B"。

### 6.2 常驻内存：严格线性

用 `--footprint` 模式测量（构建对象图前后各一次 full GC，取 `GC.GetTotalMemory(true)` 差值）：

| 形态 | 1 000 点 | 10 000 点 | 50 000 点 | 每点 |
|---|---|---|---|---|
| 树形（10 个子组） | 0.41 MB | 3.73 MB | 18.27 MB | ~383–432 B |
| 组合式（1 Cbnt + N 子测点） | 0.34 MB | 3.31 MB | 16.53 MB | ~347 B |

**结论**：

- 常驻内存是**一次性、线性**的：1 万点位约 **3.3–3.7 MB**，5 万点位约 **16–18 MB**（托管对象图，不含 XML 源文本与业务数据）。
  这个量级对现代进程很小，**不构成部署障碍**。
- 组合式比树形略省（少一层测点对象、`TagUnion` 包装与描述符），所以在点位密集时优先用组合式测点，
  内存与遍历成本都更低。
- 这里是**下限**：真实项目还会持有 XML、字符串与业务侧对象；基准只量"本库自己的对象图"。

> 判断标准：**看"每轮分配"决定要不要优化**（它影响 GC 频率），**看"常驻内存"决定能装多少点**（它只影响一次性的堆占用）。
> 两者都不是"点位数越多每轮越慢"的原因——每轮成本是线性的 ns/点，而分配是常数。

## 结论速览

| 关注点 | 数字 | 含义 |
|---|---|---|
| 框架遍历 | **8.4–9.4 ns/点、每轮 0 B** | 1 万点约 0.094 ms/轮，且不产生垃圾 |
| 判脏扫描（每轮一次） | 5 ns/点 | 全树干净时走完全部节点；10k ≈ 50 µs |
| 组合分发 | 2.6 ns/点、逐点零分配 | 点位多本身不是问题 |
| **常驻内存** | **~350–390 B/点；1k≈0.4 MB、10k≈3.5 MB、50k≈17 MB** | 与点位数线性，一次性占用，不构成部署障碍 |
| **每轮分配** | **1k 与 10k 都是 0 B** | 高频采集的 GC 压力与点位数无关 |
| S7 通道读 | 0.59 µs/次、832 B（与数据量无关） | 仅影响直读点位（兜底用法），PLC 决定实际耗时 |
| Modbus cache 复用 | 每轮省 88–280 B | 不值得改公开接口 |
| 指标记录 | 3.6 ns / 0 B；订阅后 5.8 ns | 可以放心常开 |

> 分配**按点位线性放大**只发生在"直读点位"（DirectTag）形态：S7 每点一次地址解析 ≈832 B。
> 但 DirectTag 是兜底用法，正常应把点位组织成 `TagCbnt`——那时一次硬件读 + 零分配分发，没有这个问题。

## 维护约定

- 新增基准：一个类一个关注点，`[MemoryDiagnoser]` 必开；**必须**能说明“这组数字能/不能得出什么结论”，
  避免把桩实现或回环网络的结果当成端到端性能。
- 基准结果不设门槛（机器差异会让它变成随机红）；它只用来做改动前后对比。
- 改动热路径（遍历、组合通知、驱动读写）时，请顺手在本文件更新对应表格——**数字过期比没有更糟**。
- 改了点位的对象结构（新增字段/包装层）时，记得重跑 `--footprint`：常驻内存是**每点 ~350 B** 的线性量，
  多一个字段就是几十 B × 点位数。
