# 错误处理

## 异常分类

### **加载期**异常

和**运行期异常**不同，**加载期**抛出的异常是非常好的诊断信息。所以我们把**加载期异常**统一收敛到一个异常族，调用方一个 `catch` 就能兜住并在启动阶段快速失败：<br/>

```text
Exception                                         (BCL)
└── TagsProjectLoadException                      (abstract) 加载期错误，带 Location
    ├── TagsProjectXmlException                   XML 属性/元素值不合法（缺属性、未知枚举、数值无法解析……）
    ├── TagsProjectAddressException               地址字符串无法解析（S7 / Modbus / Hjzk / SimpleFiles……）
    ├── TagsProjectConfigurationException         配置语义不自洽（未声明通道、未注册驱动、重名测点、类型不匹配……）
    └── TagsProjectValidationException            加载期校验器聚合错误（Errors 保留全部明细）
        └── TagsProjectSchemaException            XSD 校验（EnableXmlSchemaValidation，默认关闭）
```
示例：
```csharp
try
{
    var proj = factory.Create(projRoot);
}
catch (TagsProjectLoadException ex)
{
    // ex.Location 给出出错位置，如 TagGrp(产线1)/TagCbnt(输入)/Tag(bit)、Channel(S7-3)
    logger.LogError(ex, "项目加载失败：{Location}", ex.Location);
}
```

- 校验器（XSD / 交叉引用 / 驱动工厂 / 入口通道独占 / 嵌套入口）**一次性汇总全部错误**，
  因此 `TagsProjectValidationException.Errors` 是列表；`Message` 已把全部条目拼好，直接打日志即可。
- 重名测点、未声明的通道、未注册的驱动等错误都带**完整路径上下文**（`TagGrp(a)/TagCbnt(b)/Tag(c)`），
  不再需要从字典的 "An item with the same key has already been added" 反推是哪个节点出的问题。
  分隔符用 `/`，与 `ITagGrp.Descendant("a/b/c")` 的路径语法一致，便于对照与复制。

#### 抛加载期异常时的两条硬性要求

1. **消息里必须带定位上下文**，并尽量把它同时填进 `Location`：
   - XML 元素：`element.GetLocationPath()`；
   - 已建好的测点树：`grp.GetLocationPath()`、`grp.GetLocationPath("Tag(bit)")`；
   - 只有通道/描述符时：`$"Channel({descriptor.Name})"`、`$"Tag({descriptor.TagName})"`。

   路径段用 `/` 连接，形如 `TagGrp(产线1)/TagCbnt(输入)/Tag(bit)`、`Channel(S7-3)`。
2. **不要为了分类而分类**：确实不属于任何一类时，就近选一个并把上下文写清楚，
   或直接继承 `TagsProjectLoadException` 表达"加载期失败"。

#### 第三方驱动要自定义类型

继承 `TagsProjectXmlException` / `TagsProjectAddressException` / `TagsProjectConfigurationException`，
或直接继承 `TagsProjectLoadException`——它们都能被 `catch (TagsProjectLoadException)` 接住，不会破坏使用方的统一处理。

### **运行期**异常

在**运行期**，任何异常都需要被`ITagGrpRUnner`捕获进行重试——不论这是什么异常，也不论这个异常来自哪里。运行期发生的异常，是在本类库层面、还是在更底层的BCL层面，被单独捕获并识别带来的收益不大。

所以，我们决定**不单独构建运行期异常的派生体系**，库内发生的**运行期异常**，使用语义最贴近的 BCL 类型（`ArgumentException` / `InvalidOperationException` / `InvalidCastException` / `KeyNotFoundException` 等）。

#### 运行期故障消息必须能定位现场

运行期异常最终由 `TagGrpRunner` 捕获，并交给重试策略与 `RunnerCrashed(entry, channel, ex)`。注意事件里的 `channel` 只是入口的**主通道**（`SearchChannel()`）——一个入口可以有多个通道（如 S7 + 扫码枪），所以**异常消息本身**必须能指认是哪个通道、在做什么：

1. **带通道名**：`通道({ChannelName()})`。多通道入口里没有它就无法定位，不要写成 `"会话未连接"` 这种只有状态、没有主体的消息。
2. **带操作与地址/端点**：`读取DB失败：DB1.100，长度=3`、`连接PLC失败：10.0.0.5 Rack=0 Slot=1`。
3. **带底层错误文本与错误码明细**：底层库往往只给一句 `CLI : Unknown error (0xfffffffe)`，把错误码明细（`OsSockerError=…;IsoTcpError=…;S7Error=…`）与内层异常一起给出。
4. **不要为加前缀而包装第三方异常**：`SocketException` / `OpcException` / NModbus 的异常自带端点与协议信息，`catch` 后再抛会改变调用方能 catch 的类型，收益不抵风险。
5. **日志不要拍平异常**：用 `LogError(ex, "...")`，不要用 `LogError("...{ex}", ex.Message)`——后者丢掉异常类型与堆栈，插件加载失败时 `TargetInvocationException` 会完全不可读。

#### 驱动层：设备报的读取错误不要吞，也不要替下游解释质量

- **设备/协议报的读取失败必须抛**（如 OPC UA 的节点状态 `Bad`、PLC 的错误码）。只有抛出去才能走 `TagGrpRunner` 的"崩溃 → 断开全部通道 → 重连"恢复路径；"跳过这一项、记条日志、保留上次的值"会把重连路径掐断，并让值被无限期冻结而入口看起来还活着——**日志不是下游能用的接口**，下游只能看到异常（重试/崩溃策略、`RunnerCrashed`）和值本身。
- **不要引入"质量/可信度"概念**。数据采集就是采集：采集抖动由滤波解决；确实需要"（值, 可信度）"时，由业务**另加一个测点**（如 PLC 的状态字）表达，而不是让驱动层改变值的语义、把质量塞进异常消息或日志。
- 只有"语义上不是错误"的状态才放行（如 OPC UA 的 `Uncertain`：服务器给了值、只是它自己不确定）。
- **"什么算失败"可以做成品味问题，但默认口径不解释质量**：OpcUa 驱动在注册时接受一个可选委托
  `AddOpcUaClientSupport(checkIsFailed: (err, value) => ...)` / `AddOpcUaClientChannel(checkIsFailed: ...)`，
  默认实现是 `OpcUaValueQuality.IsFailed`（只有 `Bad` 算失败，`Uncertain` 照原样采集）。
  需要更严（把 `Uncertain` 也算失败）或更松（任何状态都照原样采集）都由使用方注入——**默认行为不替使用方决定可信度**。
- 单次轮询里**部分失败即整体失败**：一旦某点失败就抛，失败那一轮不改动任何缓存/时间戳/通知（避免"半更新的缓存"）。

#### `NotImplementedException` 什么时候是恰当的

- **扩展点契约**：默认实现"依赖通道 X，但实际通道是 Y"时（如 S7/Modbus 组合子的默认读写实现），`NotImplementedException` 表达的正是"这个默认实现没有覆盖你的组合，请提供/重写自己的实现"，是有意的设计信号，不要改成 `NotSupportedException`——那会影响"按类型 catch 后回退到自己的实现"的既有用法。
- **不可达兜底分支**：`switch` 的 `_ =>` 兜底（如 `TagContainer.Map` / `TagUnion.Map`）。这类分支严格说更适合 `UnreachableException`，但它 **net7+ 才有**，本库多目标到 net472，为此加垫片不值得；`NotImplementedException` 是可接受的既有习惯。


#### 静默失效一律改成显式失败

"配错了 / 用错了"要让它立刻可见，而不是退化成默认值或"什么都没发生"：

| 场景 | 曾经的写法 | 现在 |
|---|---|---|
| OPC UA 通道/服务端选项字段解析失败（如 `UsePassword="maybe"`） | 静默降级成默认值（把"配错了"伪装成"配对了"） | `TagsProjectXmlException`，消息带 `Channel(名)` |
| 测点被标记为脏，但缓存里没有该测点的值 | 直接取下标（抛无消息的 `KeyNotFoundException`）或跳过 | 抛 `InvalidOperationException`，消息带通道名 + 测点名 + NodeId |
| S7 组合自身写了相对地址（`$$100`） | 每轮轮询都抛"不支持的地址区域类型=None"，指向内部概念 | 加载期拒绝（`TagsProjectAddressException`），消息说明"组合自身必须写绝对地址" |

判断依据：正常路径不会出现这些情况（例如 `Value` setter 会先写缓存再标脏），只有绕开正常路径才可能——那就属于使用方错误，应当立刻报出来。

#### 清理路径：吞掉但必须留痕

关闭/释放/断开这类清理动作里，**一个失败不应阻断其它清理，也不应覆盖原始异常**（所以异常被吞掉），但**不能静默**：一律 `LogWarning(ex, "...")`，并带上 `ProjectRoot` 或通道名。涉及 `TagsProjectCtrl`（释放项目、取消、逐通道断开、事件派发）与 `TagGrpRunner`（断开、等待断开策略）共 8 处。

## 决策树

面向**驱动作者 / 二次开发者**：新代码要报告一个错误时，按下面的树选择类型。

```text
要报告一个错误
├─ 发生在运行期（读写 / 连接 / 轮询 / 清理）？
│   └─ 是 → 用语义最贴近的 BCL 类型或者自定义异常类型，且**绝不抛裸 Exception**
│            · 入参为空 / 越界 / 取值不合法 → ArgumentNullException / ArgumentOutOfRangeException / ArgumentException
│            · 调用时序或对象状态不对（未连接、未启动、地址区域与操作不匹配） → InvalidOperationException
│            · 类型不符 → InvalidCastException        · 按名查不到 → KeyNotFoundException
│            · 能力不支持 → NotSupportedException      · 底层超时/数据损坏 → TimeoutException / InvalidDataException
│            · 消息里必须带"通道名 + 操作 + 地址/端点 + 底层错误文本"（见上文「运行期故障消息必须能定位现场」）
│            不要为了"看起来统一"而把运行期错误塞进 TagsProjectLoadException；
└─ 发生在加载期（解析 XML / 解析地址 / 构建测点树 / 执行加载期校验）？
    └─ 是 → 这个错误是怎么被发现的？
        ├─ 读 XML 属性/元素时，这个值本身就不合法
        │   (缺 name/driver 等必填属性；endian/access 是未知枚举；
        │    scanInterval / tagSize / maxlen / Port / Rack / Parity … 解析失败)
        │   └─→ TagsProjectXmlException
        ├─ 把字符串解析成"测点地址"时失败
        │   (S7 的 DB/MB/$$ 地址、Modbus 的 <slave>~<area><start>[.<bit>]、
        │    Hjzk / ZLan 的引脚地址、位地址越界)
        │   └─→ TagsProjectAddressException
        ├─ 由"加载前扫描整个项目"的校验器发现，且一次性汇总多条错误
        │   ├─ 就是 XSD 校验（EnableXmlSchemaValidation）→ TagsProjectSchemaException
        │   └─ 其它校验器（交叉引用 / 驱动工厂 / 入口通道独占 / 嵌套入口 / 第三方）
        │       └─→ TagsProjectValidationException（Errors 保留全部明细）
        └─ 构建测点树的过程中，配置语义不自洽
            (引用了未声明的通道；driver 未注册工厂；同一父节点下测点重名；
             测点种类或地址区域不被该驱动支持；通道类型与测点要求不匹配)
            └─→ TagsProjectConfigurationException
```

### 三条容易判错的边界

| 拿不准的情况 | 怎么选 |
|---|---|
| `endian="Tiny"`（值本身读不出来） vs `channel="S7-99"`（值读得出来，但对不上任何声明） | 前者 `TagsProjectXmlException`；后者 `TagsProjectConfigurationException` |
| S7 地址 `DB200.x`（解析失败） vs DI 测点却配了 4x 寄存器地址（解析成功，但区域不被支持） | 前者 `TagsProjectAddressException`；后者 `TagsProjectConfigurationException` |
| 发现时机是"加载前批量扫描"还是"构建过程中立刻发现" | 批量 + 汇总多条 + 有 `Errors` → `TagsProjectValidationException`；发现即抛、一次一条 → `TagsProjectConfigurationException` |

> 校验器聚合异常（`TagsProjectValidationException`）的 `Location` 为 `null`——
> 它一次报告多处错误，定位信息在 `Errors` 的每一条里，不在顶层。
