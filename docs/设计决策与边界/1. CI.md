
CI 强制测试（`.github/workflows/dotnet.yml` 构建+测试、发版见 `release-nuget.yml` / `release-baget.yml`）
  
## CI OS环境

### 发版（`release-nuget.yml` 发正式源 `nuget.org`，`release-baget.yml` 发私有源）

采用`windows-latest`，同时针对`net472`+`net8`，`-c Release`构建与测试，然后发布。注意：不要改成`linux`环境，原因是我们把发版工作流作为跨平台的兜底。

策略：发布新版只通过云端跑完整的在线自动化构建、测试、发版，不应该在本地强推。

已分化完成：`release-nuget.yml`（正式版 → nuget.org，走 OIDC 临时密钥）与 `release-baget.yml`（预览/内部验证 → 私有源）。`1.0.0` 已于 2026-10-07 发布到 nuget.org。

### 构建（`dotnet.yml`）

最初是用 **windows-latest** 跑完整解决方案（net8.0 + net472 + wpf samples+ 覆盖率上报）;

后来短暂引入过 **ubuntu-latest**单独跑net8，变成两种`OS`都跑。但 Windows runner 又贵又常排队，考虑到发版工作流（windows-latest）在发版时本来就会全 TFM 跑一遍测试做兜底，而发版时的等待并不是什么不可接受的事，所以现在砍掉了 Windows job，**收敛成单一 Linux job**。

现状：`dotnet.yml` 只有 `ubuntu-latest`，负责构建（覆盖 net472 **编译**）+ `-f net8.0` 测试 + 覆盖率上报（原来在 Windows job 里）——codecov 的组件门槛只按目录划分、与 TFM 无关，所以挪到 Linux 不影响门槛，且 net472 专属分支在 net8.0 构建里不参与编译、不会被误记为未覆盖。

**tradeoff（有意接受）**：

- 云端：**PR/推送**阶段不再**执行** net472 的测试，net472 回归只会在**发版**时暴露； 
- 本地：我本人用`windows`开发，日常性跑自动化测试有兜底；合入PR前务必在`windows`上跑一遍完整自动化测试；改 `Compat/*` 或 `#if NETFRAMEWORK` 分支时务必在 Windows 上一次 `-f net472`。

所以代价可控，换来的好处是测试覆盖率没有降低的前提下日常构建更快。

#### net472 的运行测试：`net472-on-mono` job

`net472`的麻烦在于`.NET Framework`是个`Windows-only`。有意思的是，前者可以跑在`mono`上。稍微可惜的是，微软为了推“one dotnet”政策，`mono`自2024年之后就不再更新:

> The Mono Project (mono/mono) (‘original mono’) has been an important part of the .NET ecosystem since it was launched in 2001. Microsoft became the steward of the Mono Project when it acquired Xamarin in 2016.
> 
> The last major release of the Mono Project was in July 2019, with minor patch releases since that time. The last patch release was February 2024.

不过，好消息是，`.NET Framework`自身几乎也没有什么更新了 :P，所以这哥俩的兼容性基本不会再有什么变化了。

把 `mono` 装到 `Linux` 上跑 `net472`，这是一个不增加任何成本的测试途径，也无需排队等待。于是我们加了第二个 job `net472-on-mono`：

- 固定**`ubuntu-22.04`**：该镜像**预装 Mono 6.12**，省掉 `apt-get install mono-complete`（当前的 `ubuntu-latest`/24.04 不带 mono，要自己装数百 MB）。镜像退役后改成 `apt-get install -y mono-complete` 即可。
- **`continue-on-error: false`（默认，即硬性把关）**：**mono ≠ .NET Framework**。两者在 `System.IO.Ports`（ComScanner 的 net472 路径）、OPC UA 的证书/加密栈、`LogicetLoader` 的 `Assembly.LoadFrom` 分支、`System.Text.Json` 的 net472 资产、全球化/时区等方面都有差异。权威结果仍归**发版工作流**（`release-nuget.yml` / `release-baget.yml`，windows-latest 全 TFM）+ 开发机 Windows。所以 mono 绿只能说明"大概率没退化"；如果将来出现 mono 专有的伪失败，在 job 上设 `continue-on-error: true` 即可降级为"不卡 PR"的补充信号。
- 另外 mono 本身已停更（6.x 之后进入维护期）。

顺带说明一个易误解的点：本仓库是 **public**，GitHub 托管的 runner 对公开仓库**免费**——所以 Windows runner 的痛点是**排队**，不是钱。

### 本地在 WSL/Linux 上跑测试

#### `net8.0`下的测试环境

- 通常只需要跑**net8.0**：`dotnet test src/StdUnit.Tags.Tests/StdUnit.Tags.Tests.csproj -f net8.0`。

本项目目前使用`8.0.102`版的`dotnet-sdk`，安装脚本为：
```bash
> curl -L https://dot.net/v1/dotnet-install.sh -o dotnet-install.sh
> chmod +x ./dotnet-install.sh
./dotnet-install.sh --version 8.0.102
```

#### `net472`下的测试环境

Linux 上跑 `-f net472`测试，需要`mono`作为 .NET Framework 的测试宿主，没装就直接 `Could not find 'mono' host` 并让**整次** `dotnet test`（不带 `-f` 时）以 "Test Run Aborted" 收尾。

`ubuntu-22.04`自带`mono`，但`ubuntu-24`没有，可以使用 `apt-get install -y mono-complete`安装。

备注： `mono` 运行时和 `.NET Framework`不完全兼容，`Assembly.LoadFrom`、加密、全局化、线程池等行为都有差异——它的成功与否，都不必然意味着`.NET Framework`的成功或者失败。真正的`net472`+`.NET Framework`需要本机 Windows 手动跑 + 发版工作流自动跑（发版时的 windows-latest）。


## 备注：

### 小写敏感性在`WSL`上测不出来


CI 第一次跑 Linux 时红过一个测试（`TagsProjectSchemaTests`），原因是**大小写**：测试里写的是 `Schemas/drivers`，而 csproj 的 `Link` 是 `Schemas\Drivers`。Windows 不区分大小写所以一直绿，Linux 区分所以 `DirectoryNotFoundException`。

两个要点：

- **WSL 上验证不出来**：`/mnt/d`（DrvFs）同样不区分大小写。要真验证必须把仓库复制到 WSL 的 ext4，例如
  `tar cf - --exclude='./.git' --exclude='*/bin' --exclude='*/obj' . | (cd /root/casecheck && tar xf -)`，
  然后在副本里 `rm -f paket-files/paket.restore.cached`（`obj/` 没复制，paket 需要重新生成 `*.paket.resolved`）→ `dotnet tool restore` → `dotnet paket restore` → `dotnet build -c Release` → `dotnet test -f net8.0 -c Release --no-build`。
  实测（该副本，ext4）：net8.0 **1029 全绿**、net472(mono) **1028 全绿**。
- 结论：**路径大小写要与产出方逐字符一致**（csproj 的 `Link`、`TestPaths.Fixture(...)`）。不要为了"容错"把读目录写成不区分大小写——那恰好把这个坑掩盖掉；写错了就让 CI 报红，然后核对 csproj 修名字。

### 测试稳定性：优先"确定化"，其次才是放宽超时

CI 要可信，测试就不能靠时间猜。做法按优先级：

1. **能等确定信号就等信号**：例如等 `StartedOrStopped` 的"已启动"事件（它在启动 hook 执行完之后才触发），而不是 `await Task.Delay(200)` 猜后台进度；等 mock 的读取钩子（`MockTagGrp.OnIsEnabledRead`）而不是"禁用 1 秒后再启用"。
2. **不能确定的才放宽秒级预算**：超时只影响"失败暴露的快慢"，断言语义不变（如把 2s→10s）。
3. **不为测试给生产 API 开口子**：例如"禁用时的轮询间隔"没有做成可注入策略——那只是时长问题、不是正确性问题。

效果：整套测试从 11s 降到 8s，同时去掉了若干偶发失败。改测试时请沿用这个顺序，别用 `Task.Delay` 兜。
