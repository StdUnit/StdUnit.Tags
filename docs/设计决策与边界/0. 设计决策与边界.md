## 一、范围：我们不做这些

本库只提供一种交互方式——**严格的串行轮询**（有意模仿 PLC 扫描周期）。因此下面这些**不是**本库的职责：

- **报警 / 联锁 / 事件管理**：那是 SCADA / MES 的事，本库只保证"把值读上来、把值写下去"。
- **历史 / 趋势 / 存储**：不落库、不做压缩、不做窗口聚合。
- **质量与可信度解释**：设备报的读取失败（如 OPC UA 的 `Bad`）视为**失败并抛异常**，不进缓存、不发明"质量位"；需要可信度就让业务另加一个测点（见[错误处理](../异常处理.md)）。
- **协议转换 / 跨设备编排**：一个通道 = 一个协议 = 一个设备；跨设备联动写在逻辑组件里。
- **隐式数值转换**：测点类型必须精确匹配（`short` 不会写给 `int`）。
- **单通道多入口并发**：见下文「一个通道只属于一个入口」。

一句话：本库是**确定性优先的数据进出层**，不是 framework，也不是平台。

## 二、模型与运行期契约

### 入口与通道

- **入口即并发粒度**：每个 `isEntry="true"` 的入口一个常驻循环；**入口之间并行、入口内部严格串行**。要更多并发就拆入口，要更少就把点并到一个入口。
- **一个通道实例只能属于一个入口**，由默认开启的 `EntryChannelExclusivityValidator` 强制。理由不只是"断开互相踩"（连接动作可以是空实现，如 SimpleFiles）：两套扫描周期会交错读写同一底层资源，两个入口的生命周期也被耦合；而要求分离的代价几近为零——再声明一个指向同一设备的 `Channel` 即可。
  - 因此**"单通道多入口并发"明确不做**：它已经不是潜在缺陷，而是"有明确报错的既定约束"。真要做，必须先放弃上面这条设计（见 `AGENTS.md` 约束 3），代价远大于收益。
- **只有最外层入口才是入口**：`ScanEntries` 遇到入口即停止下探，嵌套 `isEntry="true"` 不生效（该子树由外层入口轮询），错误配置由默认开启的 `NestedEntryValidator` 拒绝。
- **驱动不需要自己防"连接/断开并发"**：上面两条合起来就推出了这个结论——通道与入口一一对应，入口内部每轮是一条单链 `await`（`EnsureConnectedAsync` 循环 → 处理写意图 → 写 → 读 → 逻辑 → 写），断开只发生在循环退出之后（崩溃/取消清理）或停机超时兜底，而超时兜底后的新启动会被 `OnStartingException` 拒绝。所以 `EnsureConnectedAsync` 与 `DisconnectAsync` 在模型内不会并发。
  - 推论：为"可能的并发"加的信号量、以及"`SemaphoreSlim` 没 `Dispose` 会泄漏"这两类担心都不成立（`SemaphoreSlim.Dispose()` 只有在访问过 `AvailableWaitHandle` 时才真正释放内核对象）。**再提"驱动连接要加互斥"时，先回到本节。**
  - 驱动真正要守的是另一件事：**`Dispose()` 与 `DisconnectAsync()` 必须是同一条释放路径**，且**无条件释放**——不要用 `TcpClient.Connected` / `Session.Connected` 当守卫，它只是上次 I/O 的快照，半死连接上返回 `false`，恰好把最该关的句柄留了下来。
- **加载期校验器默认开启、XSD 校验默认关闭**：跨引用、驱动工厂、入口通道独占、嵌套入口这 4 个"代码校验器"在 `UseDefaults = true` 下默认生效（它们只拒绝**确定错误**的配置，且错误信息带完整路径）；XSD 校验是 opt-in（`EnableXmlSchemaValidation()`），因为"配置合法但语义不对"才是主要失效模式，且它需要显式引入 schema。

### 观测方式：事件驱动，不要跨线程读字段

- 值的**受支持的观测方式**有两种：
  1. **按测点**：`ITag.OnTagRead` / `ITag.OnTagWritten`，或 Rx / R3 的 `Watch()` / `ObserveOnRead()`；
  2. **按入口、按轮次**：`ITagsProject.SubscribeTurnProcess(entry, handler)`（返回退订句柄）——某入口一轮结束（读取输入 + 逻辑处理之后、刷写输出之前）触发一次，适合"一次拿到该入口当前值"的观察者（如界面推送流）。回调签名是 `(entry, channel, ct)`，`ct` 是项目生命周期令牌，回调里的异步操作应透传它。
- `SubscribeTurnProcess` **每个入口可以有任意多个订阅者**：按**注册顺序串行** await（总耗时相加），任一订阅者抛异常即**中断**本次通知并**原样抛出**（= 该入口本轮失败，进入 `RunnerCrashed` 的恢复路径），排在后面的订阅者本次不再被调用。所以观察者请自己 `try/catch`，也不要指望别人替你兜住异常。
  ```csharp
  using var 遥测 = proj.SubscribeTurnProcess("g1", 遥测回调);
  using var 推送 = proj.SubscribeTurnProcess("g1", 推送回调);
  ```
- `SubscribeTurnProcess` **运行前、运行中都可以订阅**：入口列表在 `Initialize` 之后固定；运行期订阅/退订**从下一轮开始生效**（正在跑的那一轮用的是它开始时读到的快照，"刚退订"的那一次可能仍被调用一次），所以"观测端比轮询晚启动"（如 WebUi 的 hub 后启动）也能补挂上。**退订就是 Dispose 返回的句柄**（幂等；项目已释放后 Dispose 是无操作）；项目已释放后**订阅**抛 `ObjectDisposedException`。"订阅/退订"做动态开关是受支持的用法——各订阅者互不覆盖。
  - 历史：该 API 早期是"每个入口一个回调、重复设置即替换"，并要求"只能在运行前设置"。前者让库自带的观测端与使用方**互相静默覆盖**，后者带来**晚挂观测静默降级**（结构树在、值流不在，只有一条 Warning 且不自愈）；两处现由"写时复制的订阅者数组 + 退订句柄"取代（读路径仍是普通字典读、零锁）。
- 启停用 `ObserveStartedOrStopped()` / `RunnerStarted`；注意 `SubscribeTurnProcess` **只覆盖"产生了轮次"**的情形，入口被禁用、项目未启动/已停止时不产生轮次，也就不会触发。
- `RunnerStarted` / `RunnerCrashed` 是**多播事件**：按注册顺序**串行** await 全部订阅者（总耗时相加），**运行期订阅/退订从下一次通知开始生效**；任一订阅者抛异常即**中断**本次通知并**原样抛出**（后面的订阅者本次不再被调用）——不做"收集全部再只抛第一个"，那等于把其余异常静默丢弃。抛出的异常等价于该入口本轮失败（`RunnerCrashed` 抛出 = 该入口停机），所以观察者请自己 `try/catch`。`RunnerStarted` 是**按入口**触发的（每次建连、以及崩溃重连后各一次），不是"项目启动一次"——项目级启停看 `StartedOrStopped`。
- **取消不是崩溃**：`StopAsync` 导致的取消不会触发 `RunnerCrashed`，也不计入连续失败、不按重试策略退避（仍会断开该入口的全部通道）。因此进到 `RunnerCrashed` 基本等价于"真故障"，可放心在那里做告警/计数。
- **启动是两阶段的（事务性）**：先为全部入口算完逻辑组件匹配（`ILogicet.MatchEntry` / `Order`，纯计算），再准备 runner、订阅事件并启动轮询。所以启动失败时不会有"跑了一半"的项目，也不会留下"Task 无人等待、令牌永不取消"的孤儿 runner——启动阶段失败会**取消并等待已启动的入口退出**再抛出（取消靠内部 linked 令牌，因此各回调的令牌实例一致，但**不保证** `==` 传给 `RunAsync` 的那个）。匹配/排序抛异常按**配置错误**处理（`TagsProjectConfigurationException`，不会重试），而不是走 `RunnerCrashed` 的恢复路径；`Enabled` 是每轮读取的，它在运行期抛异常仍算普通轮询故障。
- 事件/回调都在**轮询线程**上同步触发，拿到的已经是本轮最终结果（值 + 时间戳），不需要、也不应该再去读字段做同步。
- **不同入口的回调并行**（各入口由各自的运行器驱动）；回调必须尽快返回（要干重活就只投递到自己的队列，由独立循环消费）。回调抛出的异常不会被吞掉——等价于该入口本轮失败，会进入 `RunnerCrashed` 的恢复路径（例外：停机取消导致的 `OperationCanceledException` 不算失败），观察者请自行 try/catch。
- 直接读 `ITag.Value` 只适用于"同一轮询线程内"或"接受最终一致性"的场景（例如 `Watch(startWithCurrent: true)` 拿首帧）。**界面不要轮询字段**——那是事件该干的事。

### 时间戳：一律 UTC

`ITag.Timestamp` 与 `TagSyncEventArgs.Timestamp` 恒为 **UTC**（`DateTime.UtcNow`）。展示、落库、与本地时间比较时由调用方自行转换。

### 写入意图：容量有限，结果明确

- `ITagsProject.WriteIntent(entry, intent, out task)`：`entry` 必须是已声明的入口，否则抛 `KeyNotFoundException`。
- 队列容量 = `IntentCapacity`（默认 5，只能在运行前设置）。队列满时**返回 `false`**，并且 `task` 已被置为 `IntentWrittenException` —— 两个信号都指向"没排进去"，调用方至少要看一个。
- 每轮最多执行 `IntentCapacity` 条意图（`TagGrpRunner.DrainWriteIntentsAsync`），其余顺延到下一轮；这是**有意的限流**，不是泄漏。
- 项目释放时，未执行的意图会被置为 `IntentWrittenException`，不会静默丢弃。

### 线程模型与伸缩

- 循环内的回调（`ILogicet.ProcessAsync`、`TagGrpWriteIntent`）**必须尽快返回**：不要 `.Result` / `.Wait()` / `Thread.Sleep`，也不要写成"等待外部事件"的形态，否则与 `WriteIntent` 构成环路等待死锁（见[外部意图](../外部意图.md)）。
- 这两个回调拿到的 `ct` 是**项目生命周期令牌**（`StopAsync` 时取消），**不是**单轮超时。停机时想尽快收手就用 `if (ct.IsCancellationRequested) return;`；**不要**抛 `OperationCanceledException`——令牌没取消时抛它仍会被当成一次崩溃（触发 `RunnerCrashed` 并按策略断开重连）。也不能借它把长任务搬进回调。
- `RunnerStarted` / `RunnerCrashed` 拿到的也是同一个生命周期令牌。`RunnerCrashed` 只在真故障时触发（取消不算崩溃），但回调执行期间项目可能被停止、令牌随时可能取消；要在崩溃后做"必须完成"的清理/上报，请按 `DisconnectAllAsync` 的口径用 `CancellationToken.None`。
- 底层是同步实现的驱动（S7 / ComScanner）会实际占住线程；入口数量上到几十个时请评估线程池与设备吞吐。当前**不设并行度上限，也没有调度器扩展点**。

不过这两点并不是什么实际问题。在工厂，有3种使用场景：
- 单机设备：一台工业计算机连接单机范围内的一两台PLC和少量其它设备。比如各类视觉上位机、测试上位机。这类场景最复杂的是业务逻辑的组织。
- 线体设备：一台工业计算机连接线体内的多个机台。我个人遇见过的，最复杂的也最多是同时(高频)控制22台PLC而已。
- 工厂级MES：事实上大多工厂MES不必直连现场PLC，它们往往是工厂级或者车间级的纯软。设备开发商往往会提供一个线体级MES或者单机级上位机与工厂MES沟通。少数工厂MES会有直连现场硬件的需求，但注定这些直连都是简单的采集，不可能涉及复杂的业务逻辑。

所以我的建议是：
- 对于上位机和线体MES：并发的入口数不会太多、底层驱动是同步式(不利于扩容)，这两点问题都不大。
- 对于工厂MES：通常不需要直连设备，如果真有采集数百台设备而且还采集不过来的场景，建议拆分一下xml配置，起几个容器同时部署即可。

### 启停语义

- `StartPollAsync` 内部 `await project.RunAsync(ct)`，即它会**一直等到轮询结束才返回**——不要在前台线程直接 await 它。
- `StopAsync` 的语义是：**发取消信号 → 等待轮询循环退出（有界）→ 释放项目 → 断开通道 → 触发 `StartedOrStopped(false)`**。因此它返回之后可以放心复用通道实例、删目录、替换 XML——"已停止"事件是**确定性信号**，不是"稍后某个时刻才会真的停"。等待超时（默认 30s）只用于兜住"驱动不响应取消"的极端情况，此时记 Warning 并继续清理。
- **项目只在 `StartPollAsync` 的 `finally` 里释放**（唯一常规释放点）；只有"等待超时"那一刻才由 `StopAsync` 兜底释放，因此**"只释放一次"是硬约束**。改启停或清理路径时必须保持这个顺序。
- **热重载**：没有内建的"用新 XML 重载"API；配方是 `StopAsync()` → 重新加载 `XElement` → `StartPollAsync(...)`，注意 `hook` 里补的通道/逻辑组件需要重建。

## 三、性能取舍

- **只做"显然该做"的优化，并说清量级**。例：OpcUa 每轮都要"子测点 ↔ NodeId"映射 → 改为按子节点集合懒构建缓存（读/写共用），并做数量校验（万一加载后增删子节点就重建，而不是静默错位）。省下的是 LINQ/字符串哈希/两次 `List` 分配，**相对一次 OPC UA 往返（ms 级）可以忽略**；收益是"不再每轮做显然重复的事"与减少 GC 压力，不是吞吐瓶颈。
- **两趟遍历有意保留**（先写完整个缓存再逐点通知）：与 `TagCbnt.NotifyChildrenRead()` 语义一致——处理器里读同组其它测点不该看到半更新的缓存；合并省下的开销可忽略。
- **遍历与通知路径必须零分配，且不要在热点路径上做委托调用**（2026-11 三轮修复，都是行为等价的）：
  1. `TagUnionExtensions.ReadAsync/WriteAsync` 原先用 `TagUnion.Map` 传三个 `async` 闭包，单节点约 220 B
     （闭包 + 委托 + 状态机），1 万点位**每轮 2.19 MB**；改用 `switch`。
  2. `TagGrp.Children` / `TagCbnt.Children` 是 `IDictionary`，`foreach` 走接口会**装箱 `Dictionary.Enumerator`**，
     而它在每轮的读、写、判脏与通知路径上。改为内部存具体 `Dictionary`、公开属性仍返回 `IDictionary`（API 不变）。
  3. `SearchAccessMode` 原来用 `TagContainer.Map` + 两个委托，且每点位要查**两次**（R1W 判定 + `IsWriteOnly`）；
     改为 `TagContainer.AccessMode` 的 `switch`、只查一次，并给 `ReadAsync` 加"读同步完成就不进 async 机制"的快路径。
  4. **`access` 的继承修正为逐级冒泡**：此前只有 `ITagGrp` 沿父链递归，`ITag`/`ITagCbnt` 只查"直接父级自己配了没"，
     `Grp(RO) → Cbnt(未配) → Tag` 会被判成 `RW`。这是**语义修正**，不是性能优化。
     同时因为**访问模式是配置期属性**（加载后不再变化），解析结果缓存在 `TagUnion.CachedAccessMode` 上：
     每节点一生只解析一次，热路径只剩空值检查。**运行期修改 `Descriptor.AccessMode` 不生效，需重新加载项目。**
  结果：遍历 `1 000 → 8.7 µs / 0 B`、`10 000 → 94 µs / 0 B`（每点 8.7–9.4 ns）；
  组合分发 `5 000 子测点 → 12.8 µs / 逐点零分配`。
  规则：**热点路径不要用 `Map` + 闭包/委托做分派或取值，也不要用 `IDictionary` 接口去 `foreach`**。
- **每轮的存活探测必须是非阻塞的**：Modbus 的 `Connected` 原先用 `Socket.Poll(1000, SelectRead)` 判断链路，
  而 Windows 的计时器粒度约 15.6 ms —— 空闲连接上这一步实测 **15.9 ms/次**，且发生在每轮、每个通道的
  `EnsureConnectedAsync` 里（100 Hz 扫描根本不可能达成）。改为 `Poll(0)`（判定逻辑不变：`Poll && Available == 0`）后
  降到 **2.3 µs**。规则：**每轮路径上不要用带超时的 `Poll`/`select` 做探测**；要么非阻塞，要么靠"读失败 → 崩溃 → 重连"。
  基准见 `EnsureConnectedBenchmarks`。
- **运行器的判脏走扁平索引，且干净时不要空写**：`TagGrpRunner` 每次（重）启动时把入口子树的
  `ITag` / `ITagCbnt` 收进 `DirtyNodeIndex`（两个数组），每轮判脏从"递归走 `Children` + `TagUnion` 分发"
  （5.2 ns/点）降到两次数组扫描（2.6 ns/点）；干净时**不再执行那趟必然空转的 `WriteAsync`**（10k 点位约 81 µs）。
  两条约束：① 正确性依据是 `ITagGrp.IsDirty()` 与 `WriteAsync` 的**一致性契约**——
  "`IsDirty()` 为 false 时 `WriteAsync` 不得写入任何东西；只要子树里存在待写节点
  （`ITag` 或 `ITagCbnt` 自身的 `IsDirty`）就必须为 true"（已写进接口注释）。
  注意它**不是**"父脏必有脏子"：`ITagCbnt.IsDirty` 可以独立为 true（整块缓存重写），
  而索引收录的正是 Tag 与组合本身，所以这种情形不会被漏掉。实现违反契约会让"该写的没写"，且没有编译错误；
  ② 树结构假定加载后不变（索引随 `CollectChannels()` 同周期重建）。
- **S7 地址解析的正则提升为静态只读**：原先每次 `Parse` 都 `new Regex(...)`（实测约 10 KB + 5 µs/次），
  而解析发生在每轮读写上。静态化后单次读 6.2 µs/10.49 KB → **596 ns/832 B**。
  这 832 B 只影响**直读点位**（`DirectTag`，兜底用法）；正常把点位组织成 `TagCbnt` 时地址只解析一次加载，
  所以不再继续优化（去正则改 span 手写解析的收益只落在这条兜底路径上）。
- 这组数字都可用 `benchmarks/StdUnit.Tags.Benchmarks` 复现（`TagTreeReadBenchmarks` / `TagTreeDirtyWriteBenchmarks` / `CbntFanOutBenchmarks` /
  `S7ChannelReadBenchmarks`；常驻内存用 `--footprint`）；基准**不**进 CI，只作改动前后的对比工具。
- 已知的优化空间（未做）见 `backlog.md`（Modbus cache 复用）。S7 的读写已经改成了"调用方提供缓冲区 + `Span<byte>`"的零拷贝实现；但连接/断开的"真异步"已评估、决定不做，理由见第五节。

## 四、已知限制

- **net472 不能卸载插件**：`LogicetLoader` 在 net8 走可卸载的 `AssemblyLoadContext`，net472 退化为 `Assembly.LoadFrom`，DLL 被锁到进程退出。
- **无法表达"陈旧度"**：要判断"这个值是几秒前读的"，请用 `Timestamp` 或另加测点，不要指望驱动层给出质量位。
- **OpcUa 的 `Uncertain`** 照原样采集（服务器确实给了值），是否可信由业务判断。
- **公开面 = 接口 + DI 扩展 + 工厂/构建器**：具体实现类一律 `internal`，不要依赖它们的类型。
- **坏点的恢复是"显式失败"**：永久性坏点会让入口持续"失败 → 断开 → 重连"，退避从 500ms 涨到 30s 封顶，期间不产出新值；这是刻意的（可通过 `RunnerCrashed` 观测），而不是静默冻结。

## 五、尚未定稿（评审留档）

- 入口并发是否需要上限 / 可注入的调度策略。
- 是否需要 `TagSnapshot`（值 + 时间戳的一致读取）。
- 是否需要 `System.Diagnostics.Metrics` 观测（每轮耗时、失败次数、重连次数、意图被拒次数）。
- 是否需要"写后读回校验"选项。

### 已评估、决定不做（2026-11）

记在这里的理由是"别再被提出来一次"；其中若有哪条被推翻，请改本节而不是只改 backlog。

- **热重载 `ReloadAsync(root)`**：它要解决的事其实就是 `StopAsync` 接 `StartPollAsync`，没有独立价值，不再单列 API。
- **S7 连接/断开的"真异步"**：收益极低——PLC 的并发吞吐远小于上位机，且入口内部本来就是串行轮询；
  2026-11 起 `Thread` 包装也已删掉（连接/断开就是同步调用，有界由 Sharp7 自己的超时保证），读/写则是
  "调用方提供缓冲区 + `Span<byte>`"的零拷贝同步实现。**不要**再为它们引入异步 I/O 抽象。
- **Modbus 读路径 cache 复用**（把 `IModbusRegisterChannel.ReadRegistersAsync` / `IModbusBitsChannel.ReadBitsAsync`
  改成"写入调用方预分配 buffer"）：2026-11 用基准量过（`benchmarks/StdUnit.Tags.Benchmarks`，桩通道 + `[MemoryDiagnoser]`）：

  | 每轮寄存器数 | 现状（通道返回新数组） | 复用 Cache | 耗时差 |
  |---|---|---|---|
  | 32 | 160 B | 72 B | 无可测差异（~31 ns vs ~31 ns） |
  | 125 | 352 B | 72 B | 无可测差异（~38 ns vs ~30 ns，抖动大于差距） |

  按 100 Hz、单入口估算，省下的是 9–28 KB/s —— 相对一次 Modbus TCP 往返（ms 级，且 NModbus 自己还有缓冲分配）
  可以忽略；代价却是**公开接口签名变更**（net472 没有默认接口方法兜底）。结论：不做。
  （基准里剩下的 72 B 是 `Task` 与通知路径的固定开销，与 cache 复用无关。）
- **公开面基线（`PublicApiAnalyzers` / 反射快照测试）**：前者因额外依赖不引入，后者因"关键保证要零反射可验证"的 AOT 取向不采用；详见 `backlog.md` 第二节。
