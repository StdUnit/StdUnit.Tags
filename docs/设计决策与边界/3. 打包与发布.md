# 打包与发布

本文件记录**发布机制与打包决策**。1.0 首发到 nuget.org 是这个类库家族第一次公开露面，配套项都是那时补的。
用户可见变更见 [CHANGELOG](../../CHANGELOG.md)。

## 一、版本通道

**为了不让使用者去记"哪个包配另一个包的哪个版本"，本仓库下的所有公开包一律同号发布**。代价是"一个号位同时承担了兼容性承诺和交付批次"两件事，所以这里把它拆成两条通道：

| 通道 | 版本号 | 谁在用 | 承诺 |
|---|---|---|---|
| **正式发布** | `2.0.0` / `2.0.0-beta2` / `1.1.0`（语义化版本） | 现场用户 | 遵守 README 里"支持/实验"的分级约定 |
| **迭代产物** | `2.0.0-dev.<run>.<attempt>`（**构建号，不是语义化版本**） | 自己与公测者 | **不承诺任何兼容性**，只作"提前试" |

分级约定仍写在 README（那里是给使用者读的）：标记为"实验"的包，`<Minor>` 跳变就可能包含破坏性更新；
标记为"支持"的只有 `<Major>` 跳变才可能破坏；核心包（`StdUnit.Tags`、`StdUnit.Tags.Core`）不属于驱动/扩展，按语义化版本处理。

迭代产物由 CI 产出，**不发布到任何包源**（`dotnet.yml` 的 `build` job，push 到 `main`/`dev` 时执行）：
从该次构建页面的 Artifacts 下载 `dev-packages.zip`，解压成一个文件夹源即可：

```powershell
dotnet nuget add source <解压目录> -n stdunit-dev
```

它刻意挂在"下一个计划发布的正式号"的预发布位上：排序上低于该正式号（正式版一发就自然覆盖），
又高于此前任何正式版（装了它仍能正常往前走，不会出现版本降级）；每次构建号唯一，
所以既不需要人工判断"这算 minor 还是 major"，也不占任何正式号位。
**不要基于迭代产物做长期依赖**——它随时可能不再产出，也没有任何兼容性保证。

## 二、破坏性变更的代价

版本号一旦推上 nuget.org 就收不回，所以**破坏性变更的代价取决于写法**，而不是"攒够一批大改动"蓄力：

- **加新 API**（新方法/新类型/新属性）→ 只需 `<Minor>`/`<Patch>` 跳变 → 可以随发；
- **删除或改写已发布的 API** → 需要 `<Major>` 跳变 → 排期到下一个大版本再删。

想快速演进时就让新旧写法**并存**（旧的标 `[Obsolete("...")]`），要"删干净"时才动用大版本窗口。

## 三、发布流程

- 版本号**不写在 csproj 里**，由 `src/publish-packages.ps1` 在打包时以 `-p:PackageVersion=…` 注入：
  - **正式发布**：`release-nuget.yml` / `release-baget.yml` 的 `workflow_dispatch` 输入 `releaseVersion`
    → `-packageVersion <语义化版本>`，对 13 个项目逐个 `dotnet pack -c Release -p:PackageVersion=…` + `nuget push`。
    号由人显式给，不从文件推断（nuget.org 上的版本不可撤销，且"这次算 minor 还是 major"本身就是兼容性决策）。
  - **迭代产物（dev 通道）**：CI 只传构建号 `-DevBuildNumber "<run_number>.<run_attempt>"`，基础版本读仓库根的
    `next-release-version.txt`（单行，如 `2.0.0`），拼成 `<基础版本>-dev.<构建号>`。这样"下一个计划发布的正式号"
    只有**一处**来源，workflow 里不再出现版本字面量。
  - 本机预演：
    `cd src` 后 `dotnet pwsh ./publish-packages.ps1 -DevBuildNumber "$(Get-Date -Format yyyyMMddHHmm)" -SkipPush -OutputDir ../dev-packages`
    （`-OutputDir` 把产物集中到一处，避免 `bin/Release` 里残留的旧 nupkg 混进来；该目录被 `*.nupkg` 规则忽略，不进 git）。
  - ⚠ **维护点**：正式版发布后把 `next-release-version.txt` 改成下一个计划号（如 `2.0.1`），否则迭代产物的版本
    会低于已发布的正式版，装上它反而是降级。
  - **`release-nuget.yml`（`name: Release (nuget.org)`）**：发正式版到 nuget.org。走 **OIDC → 临时 API key**（`NuGet/login@v1` + `id-token: write`），不存长期密钥。
  - **`release-baget.yml`（`name: Release (baget.stdunit.com)`）**：发到私有测试源（预览版/内部验证），沿用 `NUGET_SOURCE` / `NUGET_KEY` 两个 secret。
- 两个工作流都是 `windows-latest` + **`-c Release` 构建与测试**（让"验的"和发的"是同一份产物），测试覆盖 net8.0 + net472（这是 net472 **运行**测试的权威结果），**不在本地强推**。
- `src/publish-packages.ps1` 会：
  - 先校验版本号格式（`<major>.<minor>.<patch>[-<prerelease>]`），不合法立即失败——nuget.org 上的版本不可撤销，手误代价大；
  - `-SkipPush` 可只打包不推送（发版前验证产物），此时不再要求 source/key；
  - `nuget push` 带 `--skip-duplicate`：发布中途失败后重跑，不会因为"包已存在"再挂一次。
- 新增会被发布的包时：把项目名加进 `src/publish-packages.ps1` 列表，并在自己 csproj 里写一行 `<Description>`。
- `StdUnit.Tags.BlazorLib` **有意不在列表内**：它只是实验场（各驱动的编辑器/设计器实现），暂不对外发布，详见 README 的备注。

## 四、包元数据

- 统一收口在 `src/Directory.Build.props`：`Authors` / `RepositoryUrl` / `PackageProjectUrl` / `PackageLicenseExpression=MIT` /
  `PackageTags` / `PackageReadmeFile`（仓库根 README 打进包），外加公共编译设置。
  （`tests/` 另有自己的 `Directory.Build.props`，只提供编译设置、不含包元数据——测试项目不发布。）
  - 此前打出的 nuspec 是 `Package Description` 占位文本 + `authors=包名` + **没有任何 license 字段**。
- **`StdUnit.Tags.OpcUaClient` 例外**：它依赖 OPC UA 栈，授权是 *OPC Foundation MIT License 1.00*（不是 SPDX 标识符），
  因此用 `PackageLicenseFile` 把该 LICENSE 打进包，而不是 `PackageLicenseExpression`。
- **不做符号包（snupkg）**：本仓库打包由 Paket 的 `PackTask` 接管，它不把 pdb 映射进 nuspec，
  `IncludeSymbols=true` 会让 `dotnet pack` 以 `NU5005` 失败（已实测）。
- `TargetFrameworks` 不放进 props（存在 net8-only 项目）；不生成 XML 文档的项目在本项目显式写 `<GenerateDocumentationFile>false</GenerateDocumentationFile>`。

## 五、依赖版本策略

- 依赖用 **Paket**，普遍带 `lowest_matching: true` ⇒ 默认取**最低匹配版本**。
- **本库只声明"最低要求"，不承诺"依赖已审计"**：`dotnet list package --vulnerable` 报出的包（如 net472 侧的 `System.Text.Json 8.0.0`、
  `OPCFoundation.NetStandard.Opc.Ua.Core 1.5.374.126`）是否升级，由**终端开发者**按自己的节奏决定——这与"类库只负责声明下限"的定位一致。
- 升依赖要显式改 `paket.dependencies` 的版本号（`lowest_matching` 不会自动抬版本），再 `dotnet paket install` 刷新 `paket.lock`。

## 六、模板包（`StdUnit.Tags.Templates`）独立演化

**它的版本号不与 `StdUnit.Tags` 系列对齐**——`0.6.0` 对应的就是 Tags `1.0.0`。模板是"脚手架"，其内容（生成的 XML、引用的包版本、注释）按自己的节奏演进，绑定大版本号只会让两边互相牵制。

因此：

- 发 `StdUnit.Tags` 新版本时**不要求**同步重发模板；只有模板内容确实需要更新时才发它。
- README 里的 `dotnet new install StdUnit.Tags.Templates` **不写版本号**（写死版本反而让人以为它必须与库版本一致）。
- 看到"模板 0.6.0 + 库 1.0.0"不要当成版本落后——这是有意的。
