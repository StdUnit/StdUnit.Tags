# 核心模型

> 本文只讲框架：库由什么构成、怎么跑、为什么这样设计。
> 详细用法见教程站点 <https://tags.doc.stdunit.com/>（AI 参考手册 <https://tags.doc.stdunit.com/assets/999.AI.markdown>）。

## 一句话

用 XML（或代码）描述「通道 + 测点 + 逻辑」，库把它跑成一个**类似 PLC 的串行轮询循环**：

```text
测点项目 ITagsProject = 通道 ITagChannel + 测点树 ITagGrp + 逻辑 ILogicet
```

| 概念 | 说明 |
|---|---|
| 通道 `ITagChannel` | 与某种底层硬件的一次连接（S7 / ModbusTcp / OpcUa / 串口 / 文件……） |
| 测点树 | 三种节点：`TagGrp` 逻辑分组（可嵌套，`isEntry="true"` 的分组是**入口**）、`TagCbnt` "一起读、一起写"的组合（减少 IO 次数的关键抽象）、`Tag` 叶子（一个寄存器 / 一位 / 一个文件） |
| 逻辑 `ILogicet` | 业务代码；库只负责调度它，不关心它做什么 |

两条贯穿全局的立场：**不做隐式数值转换**（类型不符即抛，不猜使用者的意图）、
**错误尽早暴露**（配置问题在加载期拒绝，运行期问题抛出而不是降级）。

## 运行模型

**入口是调度单位：入口之间并行，入口内部严格串行。** 每个入口一个循环：

```text
每轮：
   连接用到的通道 
   → 执行外部意图 
   → 读入数据 
   → 跑逻辑（固定顺序）
   → 刷写底层 
   → 按扫描周期等待
```

这里有意做了取舍：**用确定性换性能**——所有逻辑以固定顺序、在固定时机执行，外部变更也被编排进同一
循环（见 [外部意图](./外部意图.md)），等价于 PLC 的扫描周期。由此推出一个框架级结论：
**"入口"就是并发粒度**——需要一台设备的多个视角时，应当在一个入口里放多个通道（单入口多通道），
而不是多个入口共用一个通道（一个通道实例只允许属于一个入口，加载期校验会拒绝违规配置）。

因此，逻辑组件、和外部意图都是跑在轮询线程上的代码（`ProcessAsync`、意图委托），都要**尽快返回**，
否则会拖住同一入口后面的所有东西。

## 使能语义（isEnabled）

`isEnabled` 是**自动轮询的开关**，不是"把这个测点关掉"：

- **自动轮询**：**自顶向下**判定。入口未使能 → 整轮跳过（其下所有节点都不被考虑）；某个
  `TagGrp` / `TagCbnt` 未使能 → 该子树整块跳过（父节点跳过后子节点不再被考虑），既不采集也不刷写；
  被跳过的组合会保留脏标记，重新使能后再刷写。`Tag` 没有 `isEnabled`，跟随其所在分组。
- **手动读写**：`ReadAsync` / `WriteAsync`（含外部意图里的显式读写）**不检查** `isEnabled`。
  于是"平时禁用的测点、抓到某个信号后再手动读一次"是受支持的用法——就像 PLC 里下了使能，
  人工仍可点动。

两条路径分别对应遍历模式 `TraversalMode.RespectEnabled`（自动轮询）与
`TraversalMode.IgnoreEnabled`（手动）。`ITagGrp` 的契约里只有
`ReadAsync(TraversalMode, ct)` / `WriteAsync(TraversalMode, ct)` 这一对「真身」，
少传参数的 `ReadAsync(ct)` 是扩展方法、等价于传 `IgnoreEnabled`（`TagUnion` 上同理）；
因此实现 `ITagGrp` 时必须把 `mode` 透传给子节点，门控才不会在该层断掉。

## 失败语义

一轮里抛出的任何异常：通知 `RunnerCrashed`（可观测）→ 断开该入口子树里的全部通道 → 退避后重试。

入口既不会疯狂重连，也不会静默冻结。这也决定了驱动层的一条要求：**设备报的读取失败必须抛出去**，不要"跳过 + 打日志 + 保留上次值"——详见 [异常处理](./异常处理.md)。
